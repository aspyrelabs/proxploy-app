# Event labels inventory

This is a working document, not a spec. It lists every error, warning and
information event Proxploy currently shows a user, the label currently
displayed for it, and a plain English sentence describing what the code
actually does when that event fires. The goal is to catch labels like
`metrics.maintain` rendering as "Metrics Maintained", a label generated by
title casing the raw job identifier that tells nobody it is the housekeeping
job that prunes and rolls up old metric samples.

**How a label is currently produced.** Every job kind and audit action is a
raw identifier such as `app.install` or `metrics.maintain`. The frontend maps
known identifiers to a human label in `ACTION_LABEL`
(`frontend/src/components/activityDisplay.ts`), about 74 entries. Anything not
in that map falls through to `actionLabel()`'s automatic fallback: split the
identifier on `.`/`_`/`-`/`:`, uppercase a short list of acronyms (vm, api,
ssh, ip, tls, vnc, cpu, lxc, ct), and title case the rest. So an unmapped
`foo.bar_baz` renders as "Foo Bar Baz". Alerts are different: an alert's
title is the rule's own name, typed by whoever created the rule, so alerts
are not subject to this problem the same way; what alerts do have is a
generated message string (`render_message` in `backend/proxploy/services/alerts.py`)
worth reviewing separately, see the Warnings table below.

Status and result words (`queued`, `running`, `succeeded`, `failed`,
`canceled`, `interrupted`, `ok`, `denied`, `error`, `firing`, `resolved`) are
shown as raw lowercase text under the label, not run through this map at
all. They are included below too, split across the three sections by what
they mean, because they are events a user reads just as much as the labels
are.

Please correct the "Current label" and "What it actually means" wording
directly, or fill in "Suggested label" and leave the rest. Anywhere I could
not tell what the code does from reading it, I wrote `UNCLEAR: <what I
checked>` rather than guess.

## Warnings

Degraded states, alerts, and things that need a look but are not outright
failures.

| Identifier | Current label | What it actually means | Where it appears | Suggested label |
|---|---|---|---|---|
| `app.reaped` | App Removed | System-detected, not user-driven: the poller noticed a container it was tracking has been missing from Proxmox continuously for a while, and deleted Proxploy's local app record on its own initiative. Nobody chose to remove anything through Proxploy; the container may have been deleted outside it, or lost in some other way. | Activity feed, audit log (`actor_type: system`) | |
| job status `canceled` | canceled (raw text) | A user asked for the job to stop before it finished. The bell popover explains it as "Canceled before it finished on \<target\>." | Activity feed, bell popover, Jobs page | |
| job status `interrupted` | interrupted (raw text) | Proxploy itself restarted (deploy, crash) while this job was still queued or running. The job cannot be resumed and its real outcome is unknown; the bell popover explains it as "Interrupted on \<target\>; it may not have completed." | Activity feed, bell popover, Jobs page | |
| `job.interrupted` (notifier event, not a per-job status) | "Proxploy: N job(s) interrupted by restart" | A one-time, cluster-wide notification sent right after Proxploy restarts, summarizing every job that got marked `interrupted` by that restart. Distinct from the per-row status above; this is the aggregate announcement. | Notification channels (email, webhook, etc.), not the activity feed | |
| alert firing, metric `cpu_pct`/`mem_pct`/`disk_pct` | e.g. "host-02 CPU > 85% for 5m (now 91%)" | A host, app, or VM's CPU/memory/disk percentage has stayed above (or below) the rule's threshold continuously for at least the rule's configured duration. | alert severity | info / warning / critical | Not fixed per metric: the severity shown on an alert is whatever the admin picked when creating that rule (defaults to "warning"). Two rules on the same metric can carry different severities. | Alerts page, rule editor | |

Failures: job failures, unreachable hosts, and refusals.

| Identifier | Current label | What it actually means | Where it appears | Suggested label |

## Labels that look wrong to me

1. **RESOLVED. `metrics.maintain` was "Metrics Maintained", now "Usage
   Cleanup"** (chosen by the maintainer, 2026-08-14). It is the hourly
   housekeeping job that rolls raw metric samples into 5 minute/1 hour
   summaries and deletes samples and rollups past the retention window (48h
   raw, 14d for 5m rollups, 400d for 1h rollups).

   Two notes for anyone renaming another label after this one. "Dashboard
   cleanup" was considered and rejected: this product has no page called
   Dashboard (the nav reads Overview and Infrastructure), and the same
   samples feed the cpu_pct/mem_pct/disk_pct alert rules in
   `services/alerts.py`, so naming one screen would teach the wrong blast
   radius. And renaming the entry in ACTION_LABEL was NOT sufficient on its
   own: failure titles are derived from the identifier, so a failed run went
   on reading "Metrics Maintain Failed" until an ATTEMPT override was added
   alongside it. Check both when you rename.

2. **WITHDRAWN, this finding was wrong. `app.migrate` -> "App Migrated"**.
   `api/apps.py:602` writes this action for the SUCCESSFUL enqueue too, via
   `enqueue_and_audit(kind="migrate.app", ..., action="app.migrate")`;
   `migrate.app` is the job kind, not a rival audit action. The row was
   misleading only because a denied result reused the success label, which is
   finding 5 below, now fixed. Kept here rather than deleted so nobody
   rediscovers the same wrong conclusion.

   The original, incorrect claim follows. The identifier
   is only ever written when a migrate attempt was refused (missing
   permission, or the self-target guard blocked an unconfirmed migrate of
   Proxploy's own container). A real, completed migration is logged under a
   completely different identifier, `migrate.app`, which happens to carry the
   exact same label text. So the one identifier spelled the way a person
   would expect a completed action to read is the one that never describes
   one.

3. **`schedule.disable` -> "Schedule Disabled"**. Reads like something a
   user did by flipping a switch. It is always the opposite: the scheduler
   automatically disabling a schedule it could not run (missing handler, bad
   trigger computation), logged as a system error. A user actually turning a
   schedule off is logged as `schedule.update`, which gives no hint that
   "disabled" happened. The two are backwards from what the words suggest.

4. **`app.reaped` -> "App Removed"**. Reads identical in tense and voice to
   `app.uninstall` ("App Uninstalled") and `app.forget` ("App Forgotten"),
   both genuine user actions. `app.reaped` is neither: it is the poller
   discovering a container has been missing from Proxmox for a while and
   quietly deleting Proxploy's own record of it. Nobody removed anything
   through Proxploy. `actor_type` is `system` on this row, never `user`, and
   the label gives no signal of that.

5. **Any `result: denied` audit row reuses its action's normal success
   label.** A blocked "Host Removed", a blocked "VM Deleted", a blocked
   "Backup Restored" all read exactly like the real thing happened. The
   difference lives only in the small grey word underneath ("denied") and a
   red tint. This is not one bad label, it is a pattern that touches most of
   the destructive actions in the Information table above whenever they carry
   a typed-confirmation guard or a role check.

6. **`storage.upload` -> "Uploaded To Storage"**. The file at the top of
   `activityDisplay.ts` states the house convention is "past tense, `<Thing>
   <Verbed>`". Every other label in the map follows Subject-Verb ("Host
   Added", "VM Deleted"). This one alone is Verb-Preposition-Object, and
   reads oddly next to its neighbors.

7. **`network.guest_config` -> "Guest Network Configured"** can appear for a
   request that never wrote anything. The same identifier is audited with
   `result: error` when Proxploy fails to even *read* a guest's current NIC
   list, which happens before any edit is attempted, not only when a write
   fails partway through.
