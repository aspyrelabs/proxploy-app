# 05: API Surface

REST API under `/api/v1`, served by FastAPI (brief §4). OpenAPI docs are
auto-generated by FastAPI at `/api/docs` (Swagger UI) and `/api/openapi.json`
the full API is itself a product feature: everything the UI does is a
documented endpoint callable with an API key (`api_keys` table,
`Authorization: Bearer ppk_…`), gated by entitlement `api.tokens`.

## Conventions

- **Auth**: session cookie (browser) or API-key bearer token (automation).
  Both resolve to a user; pycasbin then checks `(user, team-domain, resource,
  action)` (brief §5).
- **Roles** are hierarchical: `owner` ⊃ `admin` ⊃ `operator` ⊃ `viewer`. The
  table lists the *minimum* role.
- **Entitlement column**: the flag key checked server-side via the
  `Entitlements.enabled(key)` dependency (brief §7). Blank = never gated.
  During the dormant phase every flag resolves ON; the check is still
  executed on every request so arming tiers later is config, not code. Every
  key used below appears in the canonical flag index in doc 01 §17.
- **Long-running operations** (install, update, lifecycle, backup, migrate)
  return `202 Accepted` with a `job` object; progress/logs come from the jobs
  endpoints + streams. Mutations are CSRF-protected for cookie auth and
  audit-logged without exception.
- Errors: RFC 9457 problem+json. Pagination: `?page=`/`?per_page=`, `X-Total-Count`.
  Rate limiting: per-IP on `/auth/*` (slowapi middleware, brief §8).
- **Self-management guardrail**: destructive endpoints (app/VM `stop`,
  `DELETE`, `migrate`) refuse the action, or require `{"confirm": "<typed
  phrase>"}` in the body, when the target resolves to the CT/host Proxploy is
  itself running on (doc 02 §9, doc 08 §1/§9).
- **A blank Entitlement cell means "never gated"**: not "forgotten." Phase 6
  found six read endpoints (`GET /storage`, `/storage/{h}/{n}`,
  `/storage/{h}/{n}/content`, `/network/bridges`, `/network/throughput`,
  `/vms/{id}/snapshots`) whose cells were blank by omission rather than by
  design; they are gated in code (`storage.view`, `storage.content`,
  `network.view`, `vms.snapshots`) and this doc was wrong. Corrected in
  Phase 6, see `docs/notes/phase-6-infra.md`.

# Streaming

Four channels. Rule of thumb: **SSE for one-way text streams** (native
auto-reconnect with `Last-Event-ID`, plain HTTP, proxy-friendly), **WebSocket
for bidirectional or binary** (terminals, VNC).

### Auth model for streams

- SSE endpoints: **session cookie** (same-origin, EventSource sends cookies
  automatically) or API-key bearer header.
- WebSocket endpoints: **one-time ticket**. Browsers cannot set headers on
  `new WebSocket()`, and putting long-lived credentials in a query string
  leaks into logs, so the client first POSTs the matching `/tickets`
  endpoint (cookie-authed, CSRF-protected, entitlement-checked there), gets a
  ~30 s single-use token bound to user + target, and passes it as `?ticket=`.
  Same pattern Proxmox itself uses (`vncticket`). Ticket redemption is
  audit-logged.

### 1. Job log stream (install/update output)

- **Path**: `GET /api/v1/jobs/{id}/events/stream`
- **Protocol**: **SSE**, strictly one-way line stream; EventSource
  reconnects automatically and resumes via `Last-Event-ID` = `job_events.seq`,
  which the archive table gives us for free.
- **Auth**: session cookie / API key.
- **Messages**:
  ```
  id: 412
  event: line
  data: {"stream":"stdout","ts":"2026-07-28T09:14:02Z","message":"Creating LXC container 150..."}

  event: progress
  data: {"pct":62}

  event: status
  data: {"status":"succeeded","result":{"ctid":150,"ip":"10.0.20.61"}}
  ```
  `status` with a terminal state closes the stream.

### 2. App/CT console + node shell (xterm bridge)

- **Paths**: `WS /api/v1/apps/{id}/console/ws?ticket=…`,
  `WS /api/v1/hosts/{id}/shell/ws?ticket=…`
- **Protocol**: **WebSocket**, a PTY is bidirectional (keystrokes up, output
  down). Backend bridges to Proxmox's own `termproxy` websocket (brief §5
  PtyBridge, no SSH involved for consoles).
- **Auth**: one-time ticket (entitlements `apps.console` / `terminal.node`
  enforced at ticket issuance).
- **Messages**: text frames both ways carrying raw terminal bytes (xterm.js
  attach-style), plus one JSON control frame type from the client:
  `{"type":"resize","cols":120,"rows":32}`. Server sends
  `{"type":"exit","code":0}` before close.

### 3. VM console (VNC proxy)

- **Path**: `WS /api/v1/vms/{id}/vnc/ws?ticket=…`
- **Protocol**: **WebSocket, binary frames**; RFB is a binary bidirectional
  protocol; noVNC speaks websocket natively. Backend calls Proxmox
  `vncproxy` to mint an upstream ticket, then transparently pipes the
  `vncwebsocket` connection (brief §5 ConsoleProxy).
- **Auth**: one-time Proxploy ticket (entitlement `vms.console`); the
  Proxmox-side vncticket never reaches the browser.
- **Messages**: opaque RFB byte stream, no Proxploy framing.

### 4. Live events (dashboard/metrics/status)

- **Path**: `GET /api/v1/events/stream`
- **Protocol**: **SSE**, one-way fan-out of small JSON deltas to every open
  UI tab; auto-reconnect matters more than bidirectionality here.
- **Auth**: session cookie.
- **Messages** (event name = TanStack Query invalidation hint, see doc 06):
  ```
  event: metrics
  data: {"targets":[{"t":"host","id":2,"cpu_pct":54,"mem_pct":71}, …]}

  event: resource
  data: {"type":"app","id":103,"change":"status","status":"running"}

  event: job
  data: {"id":88,"kind":"app.install","status":"running","progress_pct":40,"target_type":"app"}

  event: alert
  data: {"id":12,"state":"firing","severity":"warning","message":"host-02 CPU > 85% for 5m"}

  event: entitlements
  data: {"changed":true}
  ```
  The stream carries **deltas and invalidation signals**, not full documents
  clients patch or refetch through the normal REST endpoints so there is
  exactly one representation of every resource.
