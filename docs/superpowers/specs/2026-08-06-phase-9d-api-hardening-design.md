# Phase 9d — proxploy-api production hardening

**Status:** design approved 2026-08-06, plan not yet written.
**Predecessors:** [9a](2026-08-05-phase-9a-install-update-design.md), [9b](2026-08-06-phase-9b-onboarding-polish-design.md), [9c](2026-08-06-phase-9c-web-and-docs-design.md). All complete.

Doc 10's Phase 9 was one undifferentiated "Deliver" block; the 9a spec split it
into 9a–9d. This is the last of them.

## What this phase is, and what it is not

Doc 10 scopes 9d as *"proxploy-api production hardening: rate limiting, key
rotation runbook, monitoring — still resolving 'all entitled'."*

**The service has never run.** No Dockerfile, no host, no deployment config,
`sqlite:///./data/api.db` on local disk, a signing key generated by hand into a
gitignored `var/`. It exists as 5 commits and 4 tests. So "production
hardening" here means **making it ready to deploy, not deploying it** — the
same posture 9c took with the two sites.

**Explicitly out of scope:** deployment, Dockerfile, hosting, an actual
monitoring service, error reporting, and arming tiers. `tiers.yaml` keeps
`all_entitled: true`.

### Why enforcement work is bounded

Doc 11 §6 accepts free-riding rather than mitigating it: *"anyone can patch
`Entitlements.enabled()` to return true… accepted, not mitigated away"*,
because customers buy *"support, updates, and honesty, not un-patchable bits"*.
The 2026-08-06 resolution recorded in that file confirms `proxploy-app` becomes
public when ready.

Two consequences the design follows from:

1. **Caller authentication is impossible, and adding it would be theatre.**
   Any credential the app presents must live in `proxploy-app`, which is the
   one repo that goes public. A shared API secret would be extractable with one
   `grep`. It is therefore not built. What *is* built is defence against abuse
   that does not require reading source: brute force, hammering, and replay.
2. **The tier mapping is genuinely private.** `proxploy-api`, `proxploy-web`
   and `proxploy-docs` stay private permanently — the product is distributed as
   built artifacts, not source. So `tiers.yaml` and `resolve_features()` are
   not readable by customers even after `proxploy-app` opens. Patching a local
   flag remains possible; discovering or altering what the server believes you
   are entitled to does not.

**Nothing here is exploitable today.** While `all_entitled: true`, a token
grants exactly what `DEFAULT_FEATURES` already grants unconditionally. Every
item below becomes live the day tiers arm, which is the point of doing it
before that day rather than after.

## Findings this design rests on

Established by direct survey on 2026-08-06:

- **All four endpoints have zero authentication.** No `Depends` beyond
  `get_db`, no API key, no signature, no `Authorization` parsing anywhere in
  `api/licenses.py` or `api/entitlements.py`.
- **License keys are `PPL-XXXX-XXXX-XXXX-XXXX` — 16 hex chars, ~64 bits — and
  nothing rate-limits `activate`.** That is a brute-forceable bearer secret
  with unlimited attempts. `refresh_credential` is `secrets.token_urlsafe(32)`
  (256 bits), which is fine, but **nothing binds it to an install**: no
  `install_id` check on `refresh` or `revoke`, no signature, no session.
  `_h()` is a bare unsalted `hashlib.sha256` lookup.
- **There is no logging at all.** Zero hits for `logging`/`logger`/`structlog`
  in the package — not even `logging.basicConfig`.
- **`/v1/health` returns `{"status": "ok"}` unconditionally**, with no DB
  check, no key check, no version.
- **A missing signing key crashes at startup** — `settings.signing_key_file.
  read_text()` in the lifespan raises an uncaught `FileNotFoundError`.
- **The API has no rotation concept.** `Settings.kid` is one string used for
  every token. The *app* side already holds a set (`BUNDLED_PUBLIC_KEYS` plus
  an optional `ent_extra_keys_file` overlay) precisely so rotation is an
  overlap window rather than a flag day.
- **`proxploy-app`'s `LicenseClient` has `activate()` and `refresh()` but no
  `revoke()`**, despite the API exposing `POST /v1/licenses/revoke`.
- **`signing.py::load_private_pem` is dead code** — `main.py` inlines the
  equivalent logic and never imports it.
- **`proxploy-app` already uses `slowapi`** (`api/auth.py`: module-level
  `Limiter(key_func=get_remote_address)`, `@limiter.limit("10/minute")` on
  login and TOTP, `app.state.limiter` set in `main.py`, relying on the generic
  RFC 9457 problem handler for 429s rather than a bespoke one). That is the
  house pattern and 9d follows it rather than inventing a second one.

## Design

### §1 — Postgres replaces SQLite

`Settings.db_url` defaults to a Postgres DSN. Tests run against Postgres too —
an embedded or ephemeral instance is fine, and is the approach already used
elsewhere in this workspace when Docker was unavailable. `db.py`'s
sqlite-specific `foreign_keys=ON` connect pragma goes with it.

Per the standing rule that Aspyre Labs services use Postgres, never SQLite.
**`proxploy-app` is deliberately unaffected** — it ships SQLite-WAL as the
self-hosted default because forcing a database dependency on someone installing
a Proxmox UI into an LXC is a real adoption cost, and that database runs on the
customer's hardware, not Aspyre's.

### §2 — Rate limiting, using the house pattern

Add `slowapi` to `proxploy-api`'s dependencies and replicate `proxploy-app`'s
idiom exactly: a module-level `Limiter(key_func=get_remote_address)`,
`@limiter.limit(...)` decorators on `activate`, `refresh` and `revoke`,
`app.state.limiter` assigned once in `main.py`.

`activate` takes the tightest limit — it is the only endpoint where guessing is
a viable attack. `refresh` and `revoke` are throttled against hammering rather
than guessing, since a 256-bit credential is not brute-forceable.

`/v1/health` is **not** rate-limited: throttling a health endpoint breaks the
thing that watches the service.

### §3 — Credential hardening

**No shared API secret**, for the reason in "What this phase is" above.

#### §3.1 — The license-key format, specified

**Format:** `PPL-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX` — the literal prefix `PPL-`
followed by **five groups of five characters**, 25 characters total.

**Alphabet:** Crockford Base32 — `0123456789ABCDEFGHJKMNPQRSTVWXYZ`. It
excludes `I`, `L`, `O` and `U`, and decoding normalises `I`/`l` → `1` and
`O`/`o` → `0` and is case-insensitive. That is the property that makes a key
survive being read aloud, written down, or retyped from a support ticket.

**Entropy: 120 bits.** The first 24 characters are the random payload
(24 × 5 = 120 bits). Compare the current `PPL-XXXX-XXXX-XXXX-XXXX`: 16 hex
characters, **64 bits**.

**The 25th character is a Crockford check symbol** (the mod-37 convention,
using the extended `*~$=U` symbols). It detects every single-character error
and every adjacent transposition — the two ways humans actually mistype a key.
It is a typo detector, **not** a security control, and the spec should not be
read as claiming otherwise: an attacker generates valid checksums trivially.
Its job is to make a mistyped key fail *locally*.

**Validation order is part of the design, not an implementation detail:**

1. Prefix and length check
2. Charset check (Crockford, after normalisation)
3. Check-symbol verification
4. **Only then** a database lookup

A typo therefore never reaches the database, which is what keeps §2's rate
limit meaningful — the limiter budget is spent on real guesses, not on
fat-fingered support cases. The four steps also give four distinct failure
reasons for logging, all of which are safe to log (a malformed key is not a
credential).

**Storage stays unsalted SHA-256.** `_h()`'s current approach is correct for a
120-bit random secret and must not be "upgraded" to bcrypt/argon2 — those exist
to slow brute force against *low*-entropy human-chosen passwords. Against 120
bits of randomness there is nothing to slow down, and a KDF would only add
latency to every activation. State this in the code so a future reviewer does
not helpfully break it.

**The `PPL-` prefix is deliberate and should stay**: a fixed, greppable prefix
is what lets secret scanners (GitHub's included) recognise a leaked key.

#### §3.2 — Compatibility: no dual-accept

**The new format is the only format the code accepts.** No dual-accept branch,
no legacy path, no migration.

The only keys that exist anywhere are in local dev databases and test fixtures.
Regenerate them against the new format and delete the old generator. Carrying a
64-bit format forever — and carrying the branch that decides which format a key
is, which is itself a place bugs live — to preserve throwaway fixtures is the
wrong trade.

`scripts/create_license.py` emits only the new format. Any fixture or test that
hardcodes a `PPL-XXXX-XXXX-XXXX-XXXX` string is rewritten.

#### §3.3 — `install_id` binding, both directions

`refresh` and `revoke` currently accept a `refresh_credential` and check
nothing else. They gain an `install_id` that must match the license's current
binding.

**Mismatch — rejection, and what it must not do.**

A mismatch returns **the same response as a revoked credential** (`403`, the
existing shape). This is deliberate: `proxploy-app` already handles that
response correctly and has since Phase 1. Per doc 07 §8, on a failed refresh
the app keeps honouring its cached token until `exp`, continues honouring it
through `grace_until` (~30 days) with a non-blocking banner, and only then
falls back to `reset_builtin()` — the built-in all-on default map. So a
mismatch **ages the install down through grace to the floor** rather than
cutting it off. Nothing crashes, nothing bricks, and no new client-side
handling is needed because the path already exists.

**A mismatch must never mutate the binding.** Rejecting is the entire action.
If a mismatch revoked or rebound the license, anyone holding a stolen
credential could lock the legitimate owner out by deliberately triggering one —
turning an anti-replay measure into a denial-of-service against the customer.

**Legitimate rebind — the reinstall path.**

This is the case that becomes a support queue if it is not designed, and today
it is actively broken: **re-activating with a different `install_id` currently
returns `409`.** A customer who reinstalls on new hardware, rebuilds their CT,
or restores from backup gets a new `install_id` and is refused.

New behaviour: **`activate` with a known license key and a new `install_id`
rebinds the license and returns `200`** with a freshly minted
`refresh_credential`. The prior credential is invalidated at that moment.

This is safe because the license key *is* the owner's credential — anyone
holding it already owns the license, and there is nothing a rebind grants them
that activation did not. The `409` was protecting nothing and costing a support
ticket per reinstall.

Two properties that follow, and both are wanted:

- **The old install degrades, it does not die.** After a rebind its credential
  is invalid, so its next refresh gets the same `403`, and it ages through
  grace to the floor exactly as above. Somebody who moves machines does not
  discover their old box hard-failed.
- **Rebinds are recorded.** Each one is logged and leaves a trail in
  `issued_tokens`. A license bouncing between installs is not blocked — while
  `all_entitled` there is nothing to abuse — but it is visible, which is what
  makes it actionable later if tiers arm.

Re-activating from the *same* `install_id` keeps its current behaviour: `200`
with `refresh_credential: null`, idempotent, per the contract note already in
`api/licenses.py`.

### §4 — A health check that checks something

`/v1/health` gains a DB round-trip, a signing-key-readable check, the active
`kid`, and the service version. A missing or unreadable key becomes a reported
unhealthy state rather than an uncaught `FileNotFoundError` in the lifespan.

The distinction that matters: today the endpoint answers `ok` whenever the
process is up, which means it can only ever detect "the process died". After
this it can detect "the process is up and cannot do its job", which is the
failure mode that actually happens.

### §5 — Structured logging

The service currently emits nothing. Add structured request-path logging —
method, path, status, duration, outcome — with a hard rule: **license keys,
refresh credentials and signing key material are never logged**, in full or in
part. `_h()`-style hashes are acceptable where a correlation handle is needed.

This is the honest form of doc 10's "monitoring" for a service with nowhere to
run: emit the signal now, wire a collector when there is a host. Building
dashboards for a service that has never started would be building against a
guess.

### §6 — Key rotation, code and runbook

The API signs with one key and has no rotation logic. The app already verifies
against a *set*. The asymmetry is the whole design: rotation is an overlap
window on the verifying side, and a single switch on the signing side.

Code: explicit support for a current signing key with a documented retirement
path, so changing keys is a config change with a known-good sequence rather
than an ad-hoc file swap plus a restart.

Runbook, and it must state the bootstrap property plainly: **the app's trusted
key set ships inside the release artifact**, so a newly generated signing key
is not trusted by any install until an app release carries its public half.
Rotation is therefore always two-step and cannot be completed in one action —
sign with the old key until the release carrying the new public key has
propagated, then switch. Getting this wrong bricks entitlement refresh for
every install that has not updated.

This is the same bootstrap property `docs/runbooks/publishing-a-release.md`
records for the release-signing key, and the two runbooks should read
consistently.

### §7 — Two real gaps closed

- **`LicenseClient.revoke()`** — the API exposes `POST /v1/licenses/revoke` and
  the app cannot call it. Add the method so the client covers the API surface.
- **`signing.py::load_private_pem` is dead code.** `main.py` inlines the same
  read. Either route `main.py` through the helper or delete it; two ways to
  load a signing key is one too many.

## What this phase does not prove

- **The service still has never run outside tests.** Rate limits, health checks
  and structured logs are verified by tests, not by observing a deployed
  instance under real traffic.
- **Rotation is proven mechanically, not operationally.** The runbook describes
  a two-step sequence nobody has executed against real installs, because there
  are none.
- **Nothing here is exercised against arming tiers**, since `all_entitled`
  stays true. The hardening protects a system whose protections are currently
  moot by design.

## Decisions closed before planning

§3 originally left two things as directions rather than specifications, and
both are now settled in §3.1–§3.3: the license-key format is stated exactly
(Crockford Base32, 120-bit payload, mod-37 check symbol, `PPL-` prefix,
validate-before-DB-lookup), compatibility is resolved as regenerate-only with
no dual-accept path, and `install_id` binding is specified in both directions —
mismatch rejects without mutating state and ages the install through grace, and
a reinstall rebinds cleanly via `activate` instead of hitting today's `409`.

Nothing in this spec is left for an implementer to decide.
